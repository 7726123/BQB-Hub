# ADR-0003：使用助手手册全量注入 + 未覆盖标记协议

- 状态：已采纳（v39 初版，v40 标记协议，v41 历史修复）
- 日期：2026-08

## 背景

新增「使用助手」面板：用户可询问"软件怎么用"，由 LLM 基于内置使用手册回答。
两个候选注入方案：

- A：将整本手册全量注入 system prompt（固定文本 → prompt 缓存友好，但长）。
- B：手册分类存储，AI 通过连续工具调用检索再回答（省 token，但复杂、延迟高）。

另有需求：手册可能不全；若助手答不上来，应把**最近三轮对话**上传服务器做沉淀，
方便后续改进手册，且**不向用户显示"手册未覆盖"这类标记**。

## 决策

1. **方案 A 全量注入**：`ASSISTANT_SYSTEM = 人设（"你是 BQB Hub 使用助手，是给用户说明本软件
   怎么使用的小客服"）+ 九章使用手册全文`。理由：文本固定可命中 prompt 缓存、实现简单、
   一次调用完成回答；本助手用户量小、token 成本可忽略。
2. **限域**：system 明确要求只回答本软件问题，不答超出范围的内容。
3. **标记协议（方案 B 简化）**：AI 无法确定答案时，回答最前面输出【手册未覆盖】标记；
   客户端剥离标记（用户看到干净回答），并静默 POST 最近 3 轮对话到
   `/api/usage-assistant/miss`（落盘 `data/assistant-misses.jsonl`，每会话最多 2 次、
   每条 500 字截断、失败静默）。
4. **有记忆**：助手注入最近 20 轮对话（v41 修复：初始化必须等存储就绪，
   否则重启后历史读成空）。

## 后果

- 正面：实现简单可靠；未覆盖反馈形成"数据飞轮"，手册可持续改进；
  国内可访问性不依赖服务器（回答本身在客户端发起，若连不上服务器仅跳过上传）。
- 负面：手册增长后 system 变长（预计 4-8K token/次，成本随用量线性增长）；
  标记协议依赖 LLM 遵守指令，非 100% 稳定（可接受，漏标只损失改进样本）。
- 权衡备选（未采纳）：工具调用分步检索方案复杂度高、延迟大，等手册超长再迁移。
